# 書いたものを守る層

「ここに書いたものが消えないと信じられること」([raw](../../raw/2026-10-27_消えないと信じられること.md))は、日常のノートを tsugigami に切り替えるための前提条件である。

1 つの仕組みで全部は守れない。失い方ごとに、別の層で守る。

(2026-10-27 に nishio へ口頭で解説した内容をこのページに統合した。)

## 線 1 本の行き先

```
ペンを離す
  │
  ① 画面に線が出る(メモリ上の Doc にある)
  │
  ② 保存の列に並ぶ ──→ ③ iPad の中の保存領域(IndexedDB)に入る
  │   失敗したら開き直して再試行          │
  │                                       │ 手を止めて約 20 秒後
  │                                       ▼
  │                          ④ GitHub(nishio/tsugigami-notes)に commit される
  │                                       │
  │                                       ▼
  │                          ⑤ git の履歴に残る(上書きで消えない)
```

| 層 | 守るもの | 失い方 | 仕組み |
|---|---|---|---|
| 画面(Doc) | 書いた直後の線 | — | 線を確定した瞬間に Op として適用し、保存の列へ並べる |
| 保存の列 | まだ IndexedDB に入っていない線 | 接続切れ、一時的な失敗 | 開き直して成功するまで再試行する。失敗中は赤い帯で知らせる([finding](../findings/SafariのIndexedDB接続切れ.md)) |
| IndexedDB | iPad の中のすべて | ブラウザによる削除、アプリの削除、端末の故障 | `persist()` の申請。ホーム画面アプリは 7 日での削除の対象外とされる(未確認) |
| GitHub の repo | iPad の外の写し | 手元が全部消える | 手を止めるたびに自動で commit する([判断](../decisions/2026-10-27_GitHubの非公開repoへ自動バックアップ.md)) |
| git の履歴 | 過去のどの時点でも | 間違えて消した、壊れた内容を送った | commit を重ねるだけで、上書きで消えない |
| 書き出したファイル | 人が持ち出した写し | GitHub が使えない | 手動の書き出し・読み込み |

## ②③ iPad の中の保存: 成功するまで再試行する

**何が問題だったか**
- iPad の Safari では、アプリがしばらく裏にいると、保存領域との接続が切れることがある。以後の保存はすべて失敗する(ページを読み直せば直る)。
- 前の版は、失敗すると数秒で消える通知を出し、その保存を捨てていた。
- 裏から戻って書き続けると、画面には線が見えているのに保存されていない状態になる。アプリを閉じた時点で消える。これが一番危ない穴だった。

**今の作り**(`src/store.ts`)
- 保存はすべて 1 本の列に並べ、順に実行する。
- 失敗したら、保存領域を開き直してやり直す。間隔は 0.1 秒 → 0.5 秒 → 2 秒 → 以後 5 秒ごと。諦めない。
- 待っている線はメモリと画面に残る。
- 失敗している間は、赤い帯「保存に失敗しています(n 件待ち)」を出し続ける。直ったら「保存できました」と出す。

守りの本体は「失敗した保存を捨てないこと」である。赤い帯は、失敗を見えるようにするためのもの。

## ④ GitHub への自動バックアップ

**送るタイミング**(`src/autobackup.ts`)
- 書いて 20 秒、手が止まったとき。
- 書き続けていても 3 分ごと。ただし、ペンが紙に触れている間は始めない。
- アプリが裏に回るとき、起動したとき、通信が戻ったとき。
- 失敗したら 1 分後にやり直す。

**repo の中の形**(`src/github.ts`)

```
README.md                     ノートの一覧(GitHub 上で眺める用)
notes/<ノートID>/note.json    題名・ページ数・方眼など
notes/<ノートID>/p0001.json   1 ページ目の線(1 行に 1 本)
notes/<ノートID>/p0002.json   2 ページ目の線
```

ページごとにファイルを分けているので、書いたページのファイルだけが変わる。9,900 本のノートは全部で 8.6MB あるが、1 本書き足した後に送るのは 2〜3 ファイル([実測](../findings/GitHubへのバックアップの実測.md))。

**ダウンロードせずに「変わったか」を判定する**
- git はファイルを中身のハッシュ値(blob の SHA-1)で区別する。
- tsugigami は手元で同じ計算をして、repo の一覧(tree)にあるハッシュ値と比べる。
- 一致したファイルは送らず、違うものだけを送る。

**commit の作り方**(サーバを挟まず、ブラウザから GitHub の API を直接呼ぶ)
1. いまの先頭の commit と、そのファイル一覧を読む。
2. 変わったファイルだけを送る(blob)。
3. 「前のファイル一覧 + 変更分」で新しいファイル一覧を作る(tree)。
4. commit を作り、ブランチの先頭をそこへ進める(`force: false`)。

4 の時点で別の端末が先に書き込んでいたら、GitHub が拒否する(422)。そのときは 1 からやり直す。1 回のバックアップが 1 つの commit(「tsugigami: 1 冊を更新」)になる。

## 消さない規則

バックアップで一番まずいのは、バックアップ自身がデータを消すこと。たとえば新しい空の iPad で設定したとき、「repo を手元と同じにする」という素朴な作りだと、repo のノートが全部消える。だから次の規則にしている。

- **手元に無いノートのファイルには触らない。**
- 消すのは次の 2 つだけ。
  - 手元で「完全に削除」したと記録したノート
  - 手元にあるノートの、線が無くなったページのファイル
- 消したファイルも、git の履歴には残る。

読み込み(「GitHub から読み込む」)では、手元より新しいノートだけを取り込む。何度やっても増えない。

## 失い方ごとに何が残るか

| 起きたこと | 残っているもの | 戻し方 |
|---|---|---|
| 保存領域との接続が切れた | メモリ上の線 | 自動で再試行する。赤い帯が出ている間はアプリを閉じない |
| アプリが落ちた・閉じた | iPad に保存済みの全部 | 何もしなくてよい。開き直せばある |
| iPad が壊れた・無くした・アプリを消した | GitHub の写し(最後のバックアップまで) | 新しい iPad で同じ設定をして「GitHub から読み込む」 |
| 間違えて消した | git の履歴 | repo の履歴から古いファイルを取り出す(今は手作業) |
| GitHub が使えない | iPad の中と、書き出したファイル | 書き出したファイルを「読み込む」 |

## 設計の約束

- **失敗を黙って捨てない。** 保存できていない間は、消えない表示で知らせる。
- **手元が空でも、外の写しを消さない。** 外の写しを消すのは、人が「完全に削除」したときだけ。
- **戻し方を用意する。**
  - GitHub から読み込める。
  - ファイルから読み込める。
  - どちらも、手元より新しいノートだけを取り込むので、何度やっても増えない。
- **書き味を邪魔しない。**
  - 保存は線 1 本ぶんの差分だけ。
  - GitHub へは手が止まってから送る。ペンが触れている間は始めない。

## まだ守れていないもの

- 書いて約 20 秒以内にアプリが落ちた場合、その分は iPad の中にしかない(iPad ごと失わなければ問題ない)。
- 消しゴムやゴミ箱の「完全に削除」で消したもの。取り消しの履歴は、アプリを閉じると消える。ただし GitHub に一度送った後なら、git の履歴から戻せる。
- 履歴から昔の状態に戻す操作はアプリに無い。GitHub から古いファイルを取り出せばできる。必要になったら機能にする。
- 実機の iPad では、裏に回るときに送り切れるか、書き味に響かないかが未確認([実機でしか分からないこと](../themes/実機でしか分からないこと.md))。
