# 描く前に点列を整える

書き終わった線は、保存してある点列をそのまま描かず、描く直前に整えてから描く([smooth.ts](../../src/smooth.ts) の `renderPts`、[render.ts](../../src/render.ts) の `strokePaths`)。2026-11-10 の nishio の 2 つの指摘と、その日の 2 回のやり取りで固まった考え方をまとめたページ。経緯と却下した案は [判断ページ](../decisions/2026-11-10_平滑化は書いたときの画素の幅で.md) にある。

## 3 つの原則

1. **保存してある点列は変えない。描くときにだけ整える。** 書いたものを守る([書いたものを守る層](書いたものを守る層.md))。整え方を後で変えても、元の点列から描き直せる。保存の形も変わらないので、移行が要らない。
2. **ならす幅は、書いたときの 1 デバイス画素(格子の間隔 q)で測る。表示の倍率では測らない。** 失われた精度は書いたときに決まっていて、拡大しても情報は増えない。表示の倍率で測ると、拡大するほど幅が細くなって階段が残る。倍率ごとに線の形が変わると、ズームの途中で線が揺れる。nishio の問い「スムージングは拡大された時にはそのスケールで行うべき？」への答えは「書かれたときのスケールで」。
3. **q は点列から推定する。** 保存されていないので、隣り合う点の差がほぼすべて q の整数倍になる q を探す(`latticeStep`)。見つからない線(ほかの端末で書いた線、投げ縄で回転した線)はならさない。

## 3 つの段階

| 段階 | 何を直すか | 何が起きていたか |
|---|---|---|
| なぞり直しを除く(`dropReplays`) | 線の中の 180° の折り返し | iPad の Safari は合体イベントつきの pointermove を 2 回届ける。2026-11-10 より前に書いた線は、点の 45% がなぞり直し([finding](../findings/Safariは同じpointermoveを2回届ける.md))。入力側は同じ日に直したので、新しい線には無い |
| 格子を見つける(`latticeStep`) | — | Pencil の座標は 0.5 CSS px(1 デバイス画素)に丸められて届く。fit の倍率 1.19〜1.22 では、ノート座標で q ≈ 0.41〜0.42([finding](../findings/Pencilの座標はデバイス画素に丸められる.md)) |
| 所ごとに幅を選んでならす(`smoothAdaptive`) | 拡大したときの階段 | 格子が拡大されて段に見える。水平・垂直に近い線ほど段が長い |

## 幅を所ごとに選ぶ理由

傾き m の線の段の間隔は **q / m**。傾き 0.03 なら 33q、0.01 なら 100q。水平に近い線ほど、段をならすには広い幅が要る。一方で、幅を広げると角が丸まり、小さな字が崩れる。1 つの幅では両方を満たせない。

- 最初の版(bff2508)は幅 4q だけだった。nishio「すこしなめらかになった」。まだ気になるのは「水平に近い長めの線」。段がゆるい坂になっただけで、平らな所と小さなこぶが残っていた。
- 今の版(d4ba456)は 4q〜64q の 5 段から、所ごとに選ぶ。目安は「**広い幅で引いた線が、狭い幅で引いた線から格子の半分(0.5q)以内に収まるか**」。格子に丸めた誤差は各座標で ±q/2 なので、これより小さい差は「同じ線」とみなせる。まっすぐな所では収まるので広がり、角では収まらないので狭いまま。手の揺れのような格子より大きなうねりも、収まらないので残る。
- 選んだ幅を点ごとにそのまま使うと、切り替わる所で線が折れる。そこで線に沿ってならしてから使う。ならしで角に広い幅が混ざらないよう、先に周りの最小に揃える。

## 何が良くなり、何が残るか

| | 幅 4q(bff2508) | 所ごとに選ぶ(d4ba456) |
|---|---|---|
| 傾き 0.03 の線、真の線からのずれ(RMS) | 0.24q | 0.06q |
| 実機のゆっくり横線、細かい折れ(中央値) | 0.93° | 0.47° |
| 90° の角の最大のずれ | 0.72q | 0.72q |
| 小さな円の縮み | 0.01q 以内 | 最大 0.14q |
| ペンを離した瞬間に点が動く量(最大) | 1.6q | 1.6q |
| 重さ(Linux、1 点あたり) | 約 1µs | 5〜7µs |

数値の出どころと条件は [判断ページ](../decisions/2026-11-10_平滑化は書いたときの画素の幅で.md)。見た目の比較は [4 倍に拡大した画像](../../raw/assets/2026-11-10_ゆっくり横線の平滑化の比較_4倍.png)(上から、ならさない、幅 4q、所ごとに選ぶ)。

ここで直らないもの:

- **書いている最中の線(ライブ層)はならさない。** ペンを離すと、線が書いたときの最大 1.6 デバイス画素ほど動く。目に見えるかは未確認。見えるなら、ライブ層も同じ整え方で描く。
- **縁のアンチエイリアスの潰れ**(2026-10-28 の「ガタガタ」の正体の一つ。[計測](../findings/線のガタつきの計測.md))は、点列ではなく描き方の問題で、別に残っている。
- **鋭い折り返しで線が欠ける**(2026-11-10 の 1 つ目の指摘)は、Linux の Chromium と WebKit では再現しない。iPad での切り分けを lab に頼んである(`experiments/sharp-turns.js`、未実行)。なぞり直しを除いたことで減ったかもしれないが、確かめていない。

## 「ガタつき」は 3 回出た

同じ言葉で、別の原因が 3 回出た。言葉が同じでも、原因を測ってから直す。

1. 2026-10-28「issue #1 の見本と比べてガタガタ」: 点列は Notability と同じくらい滑らか。縁のアンチエイリアスが潰れていた([計測](../findings/線のガタつきの計測.md))。未解決。
2. 2026-11-10「水平に近い短い線を拡大するとガタガタ」: 座標がデバイス画素に丸められて届き、拡大すると格子が見えていた。幅 4q でならした。
3. 2026-11-10「(まだ)水平に近い長めの線」: 段の間隔が幅 4q より長かった。幅を所ごとに選ぶようにした。

1 と 2 の切り分けには、2026-10-28 の時点で点列が格子に揃っていることに気づけていれば早かった。その時の計測は、点の間隔 0.4 px を「合体イベントの密度」と読み、格子とは見ていなかった。さらにその一部はなぞり直しだった。

## 実機で確かめること

[実機でしか分からないこと](../themes/実機でしか分からないこと.md) の「拡大したときの階段」の行:

- 水平に近い長い線を拡大して、段がまだ見えるか。
- 字の角や小さな丸が崩れていないか。
- ペンを離した瞬間に線が動いて見えるか。
- ノートを開いたときや遠くへスクロールしたときに、描画が遅くなっていないか(iPad での計算時間は測っていない)。
