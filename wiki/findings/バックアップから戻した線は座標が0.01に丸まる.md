# バックアップから戻した線は座標が 0.01 に丸まる

## 事実

- GitHub へのバックアップは、点の座標を 0.01 に丸めて書く([github.ts](../../src/github.ts) の `round`。JSON を小さくするため)。iPad の本体は IndexedDB の Float32 を丸めずに持つ。**同じ線でも、本体にある点列と、バックアップから戻した点列は少し違う。**
- 違いは見た目にはほぼ出ない(最大 0.005、書いたときの 1 デバイス画素 q ≈ 0.2〜0.7 の数 %)。ただし、**点列から何かを推定する処理には効く**。2026-11-14 に見つかった例が `latticeStep`(格子の間隔 q の推定)。最小の差 1 つから q を決めていたので、丸めで q が数 % ずれる。速く書いた線では隣の点の差が q の 10 倍ほどになり、そのずれも 10 倍に膨らむ。結果として整数倍の判定に乗らず、格子が見つからない。見つからない線はならさない決まりなので、段のまま描かれる。
- 実物(1 冊、11 ページ)で、格子が見つからない線は 1 ページあたり 1〜210 本(最大 210 / 594)。見つかった線でも q が約 3% 小さく出ていた(0.200、本当は約 0.207)。最小二乗で合わせ直して丸めのぶんを許すようにすると、1〜5 本に減った([描く前に点列を整える](../concepts/描く前に点列を整える.md) の「2026-11-14」、テストは [tests/smooth.test.ts](../../tests/smooth.test.ts) の「GitHub から戻した線」)。

## 確度

- 丸めと、戻した線で格子が見つからないことは、実物のバックアップと単体テストで確認した。
- 「iPad の本体で見ている線には起きていない」は**推測**。Float32 の丸め(y が 1 万台で約 0.001)は q の 0.5% 以下で、判定に乗るはずだが、iPad の線で `latticeStep` を測ってはいない。

## 何に気をつけるか

- **バックアップから描いた絵は、iPad で nishio が見ている絵と同じとは限らない。** AI 側で実物を調べるときは、まず丸めのせいでないかを疑う(今回、最初に見えた「水平な長い線の段」はこれだった)。
- 点列から推定する処理(格子、なぞり直し、今後足すもの)を書くときは、0.01 に丸めた点列でもテストする。端末をまたいで戻す日が来たら、ここが本体の見え方の問題になる。
- 丸めをやめる(桁を増やす)案もあるが、repo の形を変えることになるので、今は推定の側で丸めを許している。

## 実物のノートで確かめる手順

nishio の感想が「ガタガタ」のように言葉だけで原因が決まらないとき、実機を待たずに AI 側で実物を見る手順。ノートの中身は非公開なので、作業は scratchpad でやり、repo(raw/ も含む)には写さない。

1. 非公開のバックアップ repo を scratchpad に clone する(トークンは `gh auth token`、コマンドの外に残さない)。
2. `git log --name-only` で最近書いたページ(`notes/<id>/pNNNN.json`。番号は 1 始まりで、p0012 はページ 11)を探す。
3. `note.json` の `note` と、ページの `strokes`(各線に `noteId` を足す)を、書き出しの形 `{format: "tsugigami-backup", version: 1, notes: [...], strokes: [...]}` にまとめる。
4. `RENDER_JSON=<それ> RENDER_OUT=<出力先> RENDER_VIEW=x0,y0,x1,y1,倍率 npx playwright test render-json --project=chromium` で、本体の描画で撮る([e2e/render-json.spec.ts](../../e2e/render-json.spec.ts))。ページ i の上端は y = i × 1139。
5. 線ごとの数値(`latticeStep`、`renderPts` の前後)は、`src/smooth.ts` を import する小さなスクリプトを `npx vite-node` で走らせて見る。
