# イベントごとの足し描きで線の縁が濃くなる

同じ点列でも、線を何回の `stroke()` に分けて足すかで、縁の半透明の画素が重なって濃くなる。issue #2 の「ガタガタ」のうち、入力の揺れや格子とは独立した描画の問題。2026-10-28 の [計測](線のガタつきの計測.md) にあった原因を、個人のノートや画像を使わない合成データで再現して修正した。

## 切り分け

修正前 `59cbdc4` に対し、同じ 1201 点の浅い傾きの直線を、1 回の合体イベントと、表示フレームをまたぐ 1200 回の move に分けて描いた。点列は同じで、違うのはイベントの分け方だけ。

| Windows のヘッドレス環境 | alpha が変わった画素 | alpha の最大差(0〜255) | 線全体の alpha の増加 |
|---|---:|---:|---:|
| Chromium | 1895 | 98 | 約 8.2% |
| WebKit | 1895 | 98 | 約 8.2% |

修正前の数値は live 層だけの比較。区間の丸い端が重なるため、縁の中間調が濃くなる。点列を平滑化しても、この「同じ点列で結果が変わる」問題は解消しない。旧記録では Linux の WebKit で差が小さかったが、今回は Windows の WebKit でも再現した。iPad の Safari と同一視しない。

また、筆圧を使わなくなった後も、live の胴だけは太さを 1/8 刻みに丸めていた。中ペンの指定 2.2 は 2.25 になり、wet と確定後の 2.2 と異なっていた。これも丸めを外して揃えた。上の 8.2% は丸めが共通の修正前同士の比較なので、この太さの差とは分けて扱う。

## 修正の選択

live を消し、書いている線を 1 本のパスとして表示フレームごとに 1 回描く。新しい区間を同じキャンバスへ重ね続けない。`LivePenPath` は新しい点だけを `Path2D` に追加するので、毎フレーム古い点を JavaScript で曲線に作り直す必要はない。確定後のペンも同じ曲線の組み立てを使う。

ペン先をフレーム待ちにすると遅れるため、wet はイベントごとに更新する。最後に live に描いた中点から最新のペン先・予測点までをつなぎ、次の表示フレームで胴を描いた後は wet を短く描き直す。これをしないと、速く動かしたときに胴と先端が離れたり、古い wet が胴と重なったままになったりする。ペンを離す・ノートを替えるなどの確定時には、保留中の描画を取り消す。

全体を move ごとに描き直す案は、高頻度の入力に描画回数が比例するため採らなかった。長い線だけ足し描きへ戻す案は、その線だけ同じ不具合を復活させるため採らなかった。保存点列と平滑化の強さは変更していない。

## 検証と限界

- 修正後は live と wet を合成して比較。直線・曲線・直角のいずれも、イベントの分け方による画素差は両ブラウザで 0。空白同士の比較で通らないよう alpha の量も確認。
- rAF がまだ走っていない間も線の途中に空白がなく、ペンを離して 2 フレーム待っても live / wet に線が残らない。401 点が文書に保存される。
- 10001 点を 50 move ごとに表示させる試験では、胴の `stroke` は 201 回。95 パーセンタイルで Chromium の `stroke` 呼び出し約 0.1ms、WebKit 約 1ms。フレーム待ち時間はそれぞれ約 17.3ms / 27ms。2 workers の Windows ヘッドレス環境の値で、iPad の表示遅延ではない。タイマーで 0ms の値は分解能未満を含む。
- 単体テスト 76 件、追加の描画試験と基本操作のブラウザテスト 38 件、型検査と本番ビルドが成功。

今回直したのは、書いている最中の足し描きによる縁の劣化。iPad でペンを離した後に見える品質、図解のうねり・閉じ目、平滑化前後の変化は、今回の試験では解決したと判断できない。issue #2 は実機での見え方を確かめるまで開いておく。次に確認するのは、ゆっくり引いた浅い傾きの線の「書いている間・離した直後・スクロール後」と、長い線を書いたときの追従。
