# 線のガタつきを数値で比べる

nishio が「issue #1 の見本と比べて、今書いたものはガタガタしている」と感じた([raw](../../raw/2026-10-28_線がガタガタ.md))。
見本は画像しかなく、tsugigami 側は点の列と画面の両方が取れる。両方を同じ土俵に載せるために、**画像の輪郭から揺れを測る**道具を作った: [tools/wobble.py](../../tools/wobble.py)。
nishio が tsugigami で同じ「あいう」を書き、書き出し JSON と画面のスクリーンショット(issue #2)を置いた([raw](../../raw/2026-10-28_issue2_線がガタガタ.md))ので、実機のデータで比べた。

確度: 数値は実機で書いたデータとその画面で計ったもの。「原因」の節は推測。

## 結論(2 回目の比較まで含む)

1. **保存されている点列は、Notability の出力と同じくらい滑らか。** 同じ JSON を本体のコード(Chromium / WebKit、Linux)で描いて測ると、Notability のスクリーンショットと同等か、それ以下の揺れ。つまり入力(Pencil → pointer event → 点列)と描き方(中点の 2 次曲線)には、Notability に劣る点がほぼ無い。
2. **iPad の画面では、最後に書いた線の縁のアンチエイリアスが潰れている。** 同じスクリーンショットの中で、四角(最後に書いた線、点の間隔 0.4 px)は縁に中間調がほとんど無く(黒に隣り合う画素のうち中間調 15%)、文字(その前に書いた線)は普通(54%、Notability は 60〜68%)。撮り方の問題ではなく描画の問題(nishio の指摘)。
   - 原因は **ライブ層の描き方**: 書いている最中は move イベントごとに新しい区間だけを `ctx.stroke()` で足す([controller.ts](../../src/controller.ts) の `onMove`)。区間のつなぎ目で丸い端が重なり、縁の半透明の画素が重ね塗りで濃くなる。点が密なほど(ゆっくり書くほど)つなぎ目が増えて縁が潰れる。Chromium で同じ点列を合成イベントで書いて再現した: ライブ層は中間調 26%、ペンを離してタイルに焼き直した後は 79%(WebKit はライブ層でも 83% で、Linux の WebKit は重ね塗りで濃くならない)。
   - ペンを離すとタイルは 1 本の `Path2D` で焼き直され、ライブ層は `overlay()` で消される。Chromium ではこれで直る。**iPad では直っていない**ように見える。Safari でタイルの焼き直しも縁が潰れるのか、ライブ層が画面に残っているのかは、実機で確かめる(下の「切り分け」)。
3. **ゆっくり引いた直線のうねりは両方のアプリにある。** 四角の辺の中心線のうねりは Notability 0.30〜0.43 px、tsugigami 0.26〜0.59 px(下辺だけ 1.49 px で、これは手の大きな揺れ)。主な波長は等倍で約 50 px。手の揺れで、どちらのアプリも消していない。
4. **「あ」の横棒の 4 倍差(1 回目)は、主に手。** 同じ条件で引いた直線では差が小さいので、1 回目の見本がたまたま丁寧に書かれていたと考える。
5. **書き始めにフックと点の固まりがある。** 74 本中、最初の 1 px に 3 点以上たまる線が 53 本、書き始め 2 px の向きがその後と 60° 以上ずれる(フック)線が 25 本。Notability には無い。「あ」の縦棒の上端の小さな折れがこれ。

## 数値

### 2 回目: 同じ「あいう」+ 四角を、両方のアプリでゆっくり描いたもの

issue #2 のコメントの 2 枚(tsugigami 576 × 381、Notability 489 × 339。線の太さはどちらも約 5.2〜5.8 px)と、tsugigami の JSON(z=132 の四角、1994 点、点の間隔 0.40 px)を本体のコードで描いた画像(`e2e/render-json.spec.ts`、倍率 1.19 × dpr 2)。

| 画像 | λ=8 | λ=16 | λ=24 | λ=32 |
|---|---|---|---|---|
| Notability(iPad のスクショ) | 0.048 | 0.098 | 0.131 | 0.174 |
| tsugigami の点列を本体のコードで描く(Chromium) | 0.032 | 0.095 | 0.154 | 0.228 |
| 同(WebKit) | 0.041 | 0.095 | 0.149 | 0.216 |
| 同(手元の描き直し、PIL) | 0.034 | 0.090 | 0.148 | 0.218 |
| **tsugigami(iPad のスクショ)** | **0.059** | **0.137** | **0.199** | **0.262** |

線の縁の中間調(min(R,G,B) が 60〜240)の画素数を黒の画素数で割った比: Notability 0.25、WebKit の描画 0.36、tsugigami の iPad スクショ **0.10**(1 回目の「あいう」のスクショは 0.48 で普通)。

四角の辺の中心線のうねり(`--bar`、3 次曲線からの残差の頑健 σ、各画像の px):

| 辺 | tsugigami(iPad) | Notability |
|---|---|---|
| 上 | 0.59 | 0.42 |
| 下 | 1.49(中央に大きな山) | 0.37 |
| 左 | 0.44 | 0.43 |
| 右 | 0.26 | 0.30 |

JSON の四角を辺ごとに 3 次式に当てた残差は等倍で 0.16〜0.85 px、主な波長は 47〜52 px(手の揺れの周期)。

### 1 回目: 「あいう」だけ(窓の長さ λ より短い波長の揺れ。頑健 σ)

同じ「あいう」。見本は 1418 px 幅の画像の x 0–330, y 120–270、tsugigami は issue #2 の画像全体。線の太さはどちらも約 5.2〜5.4 px で、文字の大きさもほぼ同じ(tsugigami の画像は等倍の 2.38 倍)。

| λ | 見本 ズレ | tsugigami ズレ | 比 | 見本 角度 | tsugigami 角度 |
|---|---|---|---|---|---|
| 8 px | 0.062 px | 0.070 px | 1.1 | 4.8° | 5.3° |
| 16 px | 0.131 px | 0.169 px | 1.3 | 7.5° | 8.0° |
| 24 px | 0.199 px | 0.264 px | 1.3 | 9.2° | 10.3° |
| 32 px | 0.315 px | 0.354 px | 1.1 | 10.9° | 12.3° |

窓を広げると文字の曲がり(「あ」の輪など)が混ざるので、32 px 以上は比較に使えない。

### まっすぐな 1 画の中心線のうねり(3 次曲線からの残差、頑健 σ)

| 画 | 見本 | tsugigami(画面) | tsugigami(JSON の点列を 2.38 倍に換算) |
|---|---|---|---|
| 「あ」の横棒 | 0.18 px | 0.78 px | 0.50 px |
| 「い」の 1 画目(縦) | 0.38 px | 0.49 px | (下で曲がるので 3 次式が合わない) |

横棒の差が目立つが、2 回目の直線の比較から、これは主に手の違いと考える。

### 入力の点列(JSON、等倍 px)

- 点の間隔: 中央値 1.5 px(10% 0.4、90% 2.6、最大 3.4)。240 Hz の合体イベントが来ている間隔。
- 筆圧: 中央値 0.24(0.05〜0.53)。太さには使っていない。
- 横棒(z=70)の点列を 3 次式に当てると残差 0.21 px(等倍)。波長 10〜20 px のゆっくりした波。

## 測り方

1. 紙より暗い画素(min(R,G,B) < 120)をインクとみなし、副画素精度で輪郭を取る(`skimage.measure.find_contours`)。
2. 輪郭を 0.5 px 刻みに取り直し、長さ λ の窓で 3 次多項式を当てはめた「なめらかな線」を作る(Savitzky-Golay)。
3. 元の輪郭がそこから法線方向にどれだけ離れているか(**ズレ**、px)と、進行方向の角度がどれだけブレるか(**角度**、度)を出す。
4. 線の端(半円)や小さい折り返しは窓より小さい曲がりなので残差が出る。揺れは線全体にあるので、RMS ではなく中央値ベースの頑健な標準偏差で数える。
5. まっすぐな 1 画は `--bar` で切り出し、各列のインクの重心を中心線にして 3 次曲線からの残差を出す(窓に依らない)。

合成した線で目盛りを確かめた(なめらかな線 0.036/0.047 px、点ごとに σ=0.5 px 揺れる線 0.069/0.230 px、λ=8/16)。

本体のコードで JSON を描くには `e2e/render-json.spec.ts`(環境変数 `RENDER_JSON` が無ければ飛ばされるので、普段の e2e には影響しない):
```
RENDER_JSON=raw/tsugigami-20261028-1535.json RENDER_OUT=/tmp/out RENDER_VIEW=58,1653,225,1754,1.19 npx playwright test render-json
```

再現:
```
python3 tools/wobble.py raw/2026-10-27_issue1_テイスト.png --crop 0,120,330,270 --lam 8,16,24,32
python3 tools/wobble.py raw/2026-10-28_issue2_線がガタガタ.png --lam 8,16,24,32
python3 tools/wobble.py raw/2026-10-27_issue1_テイスト.png --bar 55,160,140,195
python3 tools/wobble.py raw/2026-10-28_issue2_線がガタガタ.png --bar 95,95,235,145
python3 tools/wobble.py raw/tsugigami-20261028-1519.json --last 7 --scale 2.38 --render out.png
python3 tools/wobble.py raw/2026-10-28_issue2_直線_tsugigami.png --lam 8,16,24,32
python3 tools/wobble.py raw/2026-10-28_issue2_直線_Notability.png --lam 8,16,24,32
python3 tools/wobble.py raw/2026-10-28_issue2_直線_tsugigami.png --bar 120,60,470,115     # 上辺
python3 tools/wobble.py raw/2026-10-28_issue2_直線_Notability.png --bar 100,60,380,120
```
(numpy, scipy, scikit-image, pillow が要る。venv に入れる。)

### 縁のアンチエイリアス(黒に隣り合う画素のうち中間調の割合)

| 画像 | 割合 |
|---|---|
| Chromium ライブ層(書いている最中、合成イベントで再現) | 0.26 |
| Chromium タイル(ペンを離した後) | 0.79 |
| WebKit ライブ層 / タイル | 0.83 / 0.85 |
| iPad スクショ 2 枚目: 四角(最後の線) | **0.15** |
| iPad スクショ 2 枚目: 文字 | 0.54 |
| iPad スクショ 1 枚目: 文字 | 0.94 |
| Notability: 四角 / 文字 | 0.60 / 0.68 |

再現は `e2e/render-live.spec.ts`(環境変数が無ければ飛ばす)。Chromium のライブ層は揺れも大きい(λ=8/16 で 0.047/0.107、タイルは 0.029/0.089)。iPad の 2 枚目(0.059/0.137)はこれに近い。

## 切り分けが残っていること(実機で)

iPad でペンを離した後も縁が潰れたままなのは、次のどちらか(推測)。
- **ライブ層が画面に残っている。** `overlay()` で `clearRect` しているが、Safari で消えた結果が表示に反映されていない可能性(`desynchronized` を付けたキャンバス)。
- **タイルの焼き直しでも潰れる。** Safari(CoreGraphics)が 1 本の Path2D でも区間ごとに塗っている可能性。

確かめ方: ゆっくり線を 1 本引いてスクリーンショット → 指で少しスクロールしてもう 1 枚(スクロールでタイルから合成し直す)。**スクロール後に滑らかになればライブ層が残っている**、ならなければタイルの焼き方。どちらでも対策はある(下)。

## 対策の候補(未実装)

- **ライブ層**: 区間を足していく描き方をやめ、毎フレーム現在の線全体を 1 本のパスで描き直す(`overlay()` が既にそうしている)。点が多い線で 1 フレームの仕事が増えるので、書き味(遅延)を実機で確かめる必要がある。折衷: 点が少ないうちは全体を描き直し、多くなったら区間を足す。
- **タイルでも潰れる場合**: 点の間隔が 0.7 px 未満の点を捨てて区間の数を減らす(線の位置は 0.35 px も動かない)、または輪郭の多角形を塗る描き方に戻す(筆圧対応の頃の方式)。

## 平滑化を足したらどうなるか(JSON での試算)

点列を弧長方向にガウス平滑化(σ は等倍 px)してから本体と同じ描き方で描き、測った。

| σ | 四角 λ=8/16/24/32 | 元の線からのずれ(等倍、90% / 最大) |
|---|---|---|
| 0 | 0.025 / 0.085 / 0.129 / 0.173 | 0.08 / 0.12 |
| 1 | 0.019 / 0.059 / 0.095 / 0.132 | 0.11 / 0.18 |
| 2 | 0.019 / 0.046 / 0.070 / 0.098 | 0.13 / 0.24 |

σ=1〜2 px で揺れが 3〜4 割減り、線の位置は 0.25 px も動かない。ただし 1. の通り、点列そのものは既に Notability と同等なので、平滑化は「ガタガタ」の主因への対策ではない。やるなら、縁の潰れを直してから。

## 書き始めのフック(対策の候補)

ペンが触れた直後の数点は動かずに固まり、その後に横へ 1〜2 px 跳ねてから進む。[controller.ts](../../src/controller.ts) の `onMove` は 0.3 px 未満の動きだけ捨てている。書き始めの数点を捨てる、または最初の数 px は向きが定まるまで描かない、という対策が考えられる。これは iPad の描画と関係なく、点列に入っている。

合体イベントは来ている(間隔 0.4〜1.5 px)。60 Hz の折れ線ではない。
