# 平滑化は表示の倍率ではなく、書いたときの画素の幅で

## 背景

nishio「水平に近い短い線を描いてから拡大した時にガタガタしている、スムージングは拡大された時にはそのスケールで行うべき？」(2026-11-10、[raw](../../raw/2026-11-10_鋭い折り返しの欠けと拡大時のガタつき.md))。

ガタつきの正体は、Safari が Pencil の座標を書いたときのデバイス画素に丸めていること([finding](../findings/Pencilの座標はデバイス画素に丸められる.md))。拡大すると、その格子が階段に見える。

## 決めたこと

- **平滑化の幅は「書いたときの 1 デバイス画素」(格子の間隔 q)に比例させる。表示の倍率には依らない。** 問いへの答えは「拡大されたときのスケールではなく、書かれたときのスケールで」。
- q は点列から推定する(隣り合う点の差がほぼすべて q の整数倍になる最大の q。[smooth.ts](../../src/smooth.ts) の `latticeStep`)。揃っていなければ(ほかの端末、投げ縄で回転した線)平滑化しない。
- 平滑化は **弧長に沿った局所 2 次回帰**(ガウスの重み、幅 σ = 4q)。
- **描くときにだけ使う。保存してある点列は変えない**。書き終わった線のパス([render.ts](../../src/render.ts) の `strokePaths`)で使い、線ごとに 1 回だけ計算してキャッシュする。書いている最中のライブ層は平滑化しない。
- 先に、Safari の二重配送によるなぞり直しを除く([finding](../findings/Safariは同じpointermoveを2回届ける.md))。

## なぜ表示の倍率ではないか

- 失われた精度は、書いたときの倍率で決まっている。拡大して見ても情報は増えない。どの倍率で見ても、真の線の推定は同じであるべき。
- 表示の倍率(画面の画素)で平滑化の幅を決めると、拡大するほどノート座標での幅が**小さく**なり、階段がかえって残る。問いが心配している方向と逆になる。
- 倍率ごとに線の形が変わると、ズームの途中で形が揺れ、タイル(倍率ごとに焼く)ごとに違う線になる。

## 比べた案(合成した線で、真の線からのずれと折れの大きさを測った)

格子 q に丸めた直線(傾き 0.03 と 0.15)、半径 5 と 20 の円、20° の V、90° の角で比べた(数値は q を 1 とする、RMS / 最大 / 折れの RMS)。

| 案 | 傾き 0.03 | 傾き 0.15 | 円 r=5 | 円 r=20 | 90° の角 |
|---|---|---|---|---|---|
| そのまま | 0.29 / 0.49 / 6.3° | 0.29 / 0.53 / 15.6° | 0.30 / 0.60 / 21° | 0.29 / 0.62 / 20° | 0.22 / 0.44 / 11° |
| ガウスで平均 σ=3q(端は点対称に延長) | 0.22 / 0.40 / 0.8° | 0.10 / 0.43 / 0.7° | 0.34 / 0.52 / 5.4° | 0.14 / 0.43 / 1.6° | 0.28 / 0.93 / 4.6° |
| **局所 2 次回帰 σ=4q(採用)** | 0.25 / 0.43 / 1.2° | 0.09 / 0.35 / 1.0° | **0.12** / 0.37 / 5.4° | 0.13 / 0.43 / 1.7° | 0.25 / 0.65 / 4.8° |
| 局所 2 次回帰 σ=6q | 0.23 / 0.42 / 0.6° | 0.07 / 0.27 / 0.4° | 0.12 / 0.34 / 5.3° | 0.11 / 0.38 / 1.4° | 0.30 / 0.94 / 4.1° |
| 局所 2 次回帰 σ=10q | 0.17 / 0.37 / 0.4° | 0.06 / 0.18 / 0.1° | 0.33 / 0.61 / 5.3° | 0.09 / 0.27 / 1.4° | 0.51 / 1.73 / 3.1° |

- **ガウスで平均する**: 小さな円が縮み、端を延長しないと線の端が内側へ引っ込む(円が閉じなくなる)。却下。
- **幅を大きく(σ=10q)**: 水平に近い長い線はまっすぐになるが、角が丸まり小さな円が崩れる。
- **格子の箱の中に留める(大きくならしてから、元の点の ±q/2 に押し戻す)、点ごとに幅を変える**: 円が多角形っぽくなり、数値も良くならなかった。却下。
- **ノート座標で固定の幅(例 1 px)**: 拡大して小さく書いた字(格子が細かい)をならしすぎる。却下。
- **保存するときに点列を書き換える / q を保存する**: 保存の形を変えずに済むので、描くときの推定にした。

σ を 4q にしたのは、6q と比べて角が丸まりにくく(90° の角の最大ずれ 0.65q と 0.94q)、ペンを離した瞬間の形の変化が小さいから。実機の 2 つの JSON(なぞり直しを除いた後)で、点が動くのは中央値 0.2q、90% 点 0.5q、最大 1.6q(書いたときの 1.6 デバイス画素)。

## 残ること

- **傾きがごく小さい線は、ゆるい段が残る。** 段の間隔が q / 傾き(傾き 0.03 で 33q)と、平滑化の幅よりずっと長いから。尖った段がなめらかな坂になるだけ。これ以上は「まっすぐ引いたつもり」を仮定することになる。
- **ペンを離した瞬間に、線が最大で書いたときの 1.6 デバイス画素ほど動く**(書き始めのフックや角)。見えるかどうかは実機で確かめる(未確認)。見えるならライブ層も同じ平滑化で描く。
- 計算の重さ: Linux の Node で 1 点あたり約 1µs(1535 の JSON の 129 本・8,789 点で 8〜9ms、温まった後)。線ごとに 1 回だけで、見えている線から順に計算されるが、ノートを開いた直後の 1 画面ぶんで数十 ms 増えうる。iPad での時間は未計測。
- 投げ縄で回転した線は格子が崩れるので平滑化されない(回転する前より粗く見えうる)。
- 鋭い折り返しの欠け(同じ日の nishio の 1 つ目の指摘)は別の問題で、iPad で切り分け中(`experiments/sharp-turns.js`)。

## 実機での反応(2026-11-10)

bff2508 を iPad で見た nishio「すこしなめらかになった」([raw](../../raw/2026-11-10_平滑化を入れた後の拡大の見え方.md))。効いてはいるが、「すこし」なので段は残って見えている可能性がある(推測。どの線・どの倍率で見たか、ペンを離した瞬間に線が動いて見えたかは聞いていない)。上の「傾きがごく小さい線は、ゆるい段が残る」がそれかもしれない。σ を上げる・傾きの小さい区間だけ広げる、などは、どこが気になるのかを聞いてから決める。
